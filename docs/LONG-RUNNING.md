# 长期运行与资源稳定性

## 是否需要换语言

VPN 数据面已经使用 C 编写的 ocserv 1.5.0 / OpenConnect 9.21，客户端为原生 C++17 / Win32。Lua 管理页不转发 VPN 数据包。当前更适合完善资源边界和异常恢复，不建议为降低内存直接重写协议核心。

Go 会增加运行时和垃圾回收开销；Rust 可改善新代码的内存安全，但包装现有 C 库仍需管理其生命周期，自行重写 TLS、DTLS、路由和认证则需要重新验证协议兼容性及 Windows 7 支持。没有测出具体瓶颈之前，无法保证换语言更快或更省内存。

## 本次改进

- 客户端队列限制待处理日志为 256 Ki 个 UTF-16 字符（约 512 KiB 字符数据）、最多 512 条、每条最多 8 Ki 字符。统计、配置刷新及中间连接状态只保留最新值；认证提示和最终状态不因日志拥塞丢失。积压期间只发送一次界面唤醒消息，定时器补偿消息投递失败。
- 日志窗口保留原有 512 Ki 字符历史上限。可见时最多每 250 ms 刷新一次，隐藏或最小化时不重绘，打开时显示最新内容。认证及重连阶段不再持续发送界面流量统计请求。
- 随包网络脚本按文件已有长度计算约 2 MiB 的 UTF-16 日志预算，包含换行及 BOM，异常日志也服从预算。客户端在脚本执行结束后的 setup、reconnect 和 cleanup 回调中读取并清空文件，正常会话清理时删除。日志拆分前统一脱敏。自定义脚本仍需自行约束输出。
- 服务端命令执行器在输出管道关闭后休眠等待子进程，不因 HUP 通知空转。超时使用 `nixio.sysinfo().uptime`，不受 NTP 校时影响；保留原有 128 KiB 输出限制、进程组终止和子进程回收。
- 管理页查询和响应体读取最多等待 15 秒，操作结果最多等待 120 秒。超时释放请求状态，后续轮询可恢复；操作超时提示先刷新核实，不自动重发修改。重复刷新共用一个请求，过时的后台响应不会覆盖正在编辑或刚刷新的页面。
- 每 3 秒轮询在 VPN 专用上网关闭时只读取事务状态，不再重复启动 OpenClash 进程及 LAN/WAN 检查命令。首次加载、手动刷新及实际开启时执行完整检查。在其他页面修改 OpenClash 或网络后，点“刷新”更新可用性；隐藏标签页仍暂停轮询。

管理页 APK 修订为 `0.4.1-r4`。安装新构建后刷新浏览器；Windows 需使用本次源码构建的新便携包。仅推送源码不会改变已经运行的 N1 或客户端。

## 已有资源边界

默认最多 32 个在线连接、同账号 1 个连接、DPD 60 秒、认证超时 240 秒、闲置重连 cookie 有效期 300 秒，压缩默认关闭，UDP 默认启用。正常长连接不会仅因 cookie 时间到期断开。客户端默认重连窗口为 300 秒，可在高级配置调整，这不等于无限重试。

VPN 专用上网事务完成后工作进程退出，日志清理进程每分钟检查一次。服务日志在 `/var/run`，最多 256 条、保留 24 小时，重启后清空。运行期事务备份以固定文件名覆盖；每次安装升级另建一份备份，不会随在线时长增加。ocserv 由 procd 监管，崩溃可重启，但这不能证明进程不会泄漏或卡住。

在线人数、连接跟踪条目、TLS 缓存和 OpenClash 的规则/DNS 缓存都会影响占用。Linux 用空闲内存做文件缓存属正常；不能仅凭“已用内存增加”认定泄漏，应比较 `MemAvailable`、各进程 RSS、句柄/文件描述符和相同负载下的趋势。

## 验证与实机观察

本地 x86/x64 资源回归各发送 60 万个模拟事件、执行 1,000 轮队列清空和提示对象释放，检查最新统计、日志容量、最终状态、句柄和真实 Win32 日志控件。内存计数覆盖队列测试进程，不使用真实 VPN 流量，不能解释为整个客户端或服务端的长期内存曲线。

服务端回归覆盖管道 EOF、输出洪峰、缓慢输出、时限及退出后尾部输出；禁用状态查询 10,000 次不启动探测命令。浏览器用真实管理页和隔离后端验证请求挂起、响应体挂起、50 次重复刷新和隐藏页暂停。构建工作流包含这些回归。

建议在实际 N1 上以固定在线人数观察至少 24–72 小时，包含断网恢复、睡眠唤醒及 OpenClash 重启。开始、稳定运行后及变慢时分别记录以下只读信息：

```sh
date
uptime
free -k
top -b -n 1
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
du -k /var/run/ocserv-easy /tmp
```

用 `top` 找出 ocserv 主进程、工作进程和实际 Clash/Mihomo 核心 PID，再分别查看 `/proc/PID/status` 的 `VmRSS`、`VmSize`、`Threads` 及 `/proc/PID/fd` 的文件数。记录所有 ocserv 进程，不能只看主进程。连接数恢复基线后，占用应趋于稳定；保持相同网站和流量条件，区分 DNS、节点延迟、UDP 不通和 CPU 饱和。

无需为了“稳定”定期清缓存或强制重启 VPN，这会中断连接，也会掩盖增长来源。本次未连接用户 N1，连续数天的实际转发、Flippy 内核及 OpenClash 行为仍需设备验证。
